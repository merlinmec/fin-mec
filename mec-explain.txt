MEC-EXPLAIN.TXT — guia de estudo do projeto fin-mec
=====================================================
(Este NÃO é um README técnico. É um guia para você conseguir explicar este
projeto pra outra pessoa — o problema que ele ataca, as decisões tomadas,
e o que estudar pra sustentar essas decisões numa conversa técnica.)


1. O QUE É O PROJETO
---------------------
"mec-fin" (artefato Maven: mec-fin, pacote com.mecfin) é uma plataforma
pessoal de gestão financeira, com arquitetura pronta para múltiplos
usuários desde o início mesmo sendo uso individual hoje. Produto de
referência declarado: o Organizze (app brasileiro de finanças pessoais).

Stack: Spring Boot 4.1 / Java 21, Postgres 18 (via Docker Compose),
Flyway para migrações, springdoc para OpenAPI, autenticação por sessão
(cookie), Argon2id para senha, Bucket4j+Caffeine para rate limiting.

ESTÁGIO REAL DO PROJETO (19/08/2026): o MVP inteiro (Fases 0-7 do
roadmap) está pronto, testado e mergeado na main — 8 módulos de domínio:

  - identity     — registro/login/logout via sessão
  - household    — espaço financeiro compartilhado (hoje 1 usuário = 1
                   household automático; schema já suporta convidar um
                   segundo membro sem migração futura)
  - account      — contas financeiras (corrente/poupança/carteira/
                   investimento), soft delete
  - category     — categorias de receita/despesa, com 6 categorias
                   padrão do sistema (visíveis a todo household, não
                   editáveis)
  - budget       — limite de gasto por categoria/mês; gasto realizado e
                   percentual consumido são SEMPRE calculados na leitura
                   a partir de transaction, nunca persistidos
  - transaction  — lançamentos: receita/despesa, transferência entre
                   contas (duas pernas pareadas), parcelamento
                   (materializa todas as parcelas na criação),
                   recorrência (só metadado, sem geração automática de
                   ocorrências futuras — decisão deliberada, ver seção 3)
  - bill         — contas a pagar, com baixa que gera uma transaction
                   real; status "vencida" também é calculado na leitura,
                   nunca persistido
  - dashboard    — sem tabela própria; agrega os outros seis módulos
                   num único endpoint (saldo, receitas/despesas do mês,
                   próximos vencimentos, gasto por categoria, orçamentos
                   do mês, previsão de saldo simples)

143 testes (54 unitários + 89 de integração via Testcontainers com
Postgres real), mvn verify limpo. Todo o histórico do git é organizado
em branch-per-fase + Pull Request (nunca commit direto na main) —
inclusive as fases 0-2, que originalmente tinham sido commitadas direto
e foram reorganizadas retroativamente (ver seção 5).

Para quem: ainda tem cara de projeto pessoal/portfólio (sem deploy em
produção, sem base de usuários real), mas a decisão de household
compartilhado desde a Fase 2 é o primeiro sinal concreto de que a
arquitetura já pensa em multiusuário de verdade, não só "um CurrentUser
por linha do banco".

O que falta pro produto ficar completo frente ao Organizze: cartão de
crédito + fatura (Fase 8), integração bancária real via Open Finance
(Fase 9, deliberadamente adiada — ver seção 2), notificações de
vencimento (Fase 10) e deploy em produção (Fase 11).


2. COMO SE COMPARA A SOLUÇÕES SIMILARES NO MERCADO
----------------------------------------------------
No mercado brasileiro, os players mais citados em comparativos de
2025/2026 são Mobills, Organizze, Minhas Economias e Spendee; o
GuiaBolso foi comprado pelo PicPay e descontinuado. O diferencial mais
citado nesses comparativos é Open Finance — conectar contas de bancos
diferentes automaticamente em vez de lançamento manual — que este
projeto deliberadamente adia para a Fase 9 (ver módulo bankprovider no
roadmap arquitetural: porta/adapter isolando o provedor, para não
acoplar Account/Transaction a um fornecedor comercial específico como
Pluggy ou Belvo antes da hora).

Na vertente open-source/self-hosted, as referências continuam sendo
Firefly III (partida dobrada / double-entry bookkeeping — toda
transação afeta duas contas) e Actual Budget (orçamento de base zero,
inspirado no YNAB). A decisão de modelagem deste projeto, agora que
existe modelo de dados real, ficou num meio-termo deliberado: não é
partida dobrada completa (uma despesa comum afeta só uma conta, não
duas) — só transferência entre contas usa um par de lançamentos
(transfer_pair_id ligando as duas pernas, cada uma com account_id e
direção OUT/IN próprios). Orçamento é por categoria/mês com limite
plano (mais perto do "envelope" do Actual Budget que da partida dobrada
do Firefly III), mas sem a exigência de alocar 100% da renda antes de
gastar (zero-based) — é limite de alerta, não bloqueio de gasto.

Posicionamento honesto hoje: o MVP cobre o núcleo funcional do
Organizze (contas, categorias, orçamento, lançamentos incl.
recorrentes/parcelados/transferência, contas a pagar, dashboard com
previsão de saldo) — falta cartão de crédito/fatura e Open Finance para
ser funcionalmente equivalente. A diferenciação real e deliberada frente
ao Organizze é o modelo de compartilhamento: o Organizze compartilha
conta via credencial compartilhada (duas pessoas logando com o mesmo
usuário/senha); este projeto modela household com membros e roles
(OWNER/MEMBER) desde a Fase 2 — login próprio por pessoa, mesmo espaço
financeiro. O convite de um segundo membro de verdade (UI/fluxo) ainda
não está implementado — só o schema, de propósito (ver seção 3).


3. DECISÕES TÉCNICAS TOMADAS E POR QUÊ
-----------------------------------------
O histórico cobre 8 fases completas agora, então dá pra ver não só
decisões isoladas, mas um padrão de disciplina se repetindo — vale
estudar o padrão tanto quanto cada decisão específica.

a) Household compartilhado, decidido cedo mesmo custando escopo extra
   (Fase 2) — dado financeiro pertence a um household_id, nunca a um
   user_id direto. Um listener síncrono (dentro da mesma transação de
   registro) cria automaticamente um household com o usuário como OWNER
   — hoje transparente (1 usuário = 1 household), mas a fronteira já
   existe pra convidar um segundo membro sem migração de schema depois.
   Essa decisão foi tratada com o mesmo peso de "Money" e "autenticação"
   no roadmap arquitetural: categoria de decisão que é cara de reverter
   depois (mudar user_id→household_id em toda tabela financeira já
   existente seria retrabalho grande), por isso decidida cedo mesmo sem
   uso imediato do multiusuário real.

b) "Derivado, nunca persistido" como padrão recorrente — não é uma
   decisão isolada, é um princípio que se repete em três módulos
   diferentes, deliberadamente, pra nunca duplicar fonte de verdade nem
   precisar de job agendado só pra manter um campo sincronizado:
     - Budget.spent / percentageUsed: somados de transaction na leitura
       (BudgetService.toView), nunca gravados.
     - Bill status OVERDUE: nunca é um valor possível na coluna do
       banco (só OPEN/PAID/CANCELED são persistidos) — é calculado
       (OPEN + due_date no passado) toda vez que o bill é lido
       (BillView.effectiveStatus()).
     - Dashboard inteiro: módulo sem tabela própria, cada request
       recalcula saldo/receita/despesa/previsão na hora, agregando os
       outros seis módulos.

c) Transaction com três "formatos" via factory methods nomeados, não um
   construtor gigante — Transaction.of() (lançamento avulso),
   Transaction.transferLeg() (uma perna de transferência, sempre criada
   em par) e Transaction.installmentLeg() (uma parcela). Evita uma
   assinatura de construtor com uma dezena de parâmetros quase sempre
   nulos dependendo do caso de uso — decisão de legibilidade que só fez
   sentido depois que o domínio cresceu (na Fase 4, com só receita/
   despesa, um construtor único ainda fazia sentido).

d) Transferência entre contas: referência mútua resolvida em duas
   etapas — a perna criada primeiro (transferLeg) não tem como saber o
   id da segunda até ela existir, então: salva a primeira, cria a
   segunda já apontando pra primeira, salva a segunda, e só então volta
   e liga a primeira na segunda. TransactionService.cancel() cascateia
   pro par inteiro (cancelar só um lado deixaria dinheiro "sumindo" de
   uma conta sem aparecer na outra), e update() bloqueia edição de uma
   perna de transferência inteira (editar só um lado dessincronizaria o
   par — a saída correta é cancelar e criar de novo).

e) Recorrência decidida como só metadado — e essa decisão foi
   REAFIRMADA quando testada de novo. Na Fase 5 (Transaction), a
   pergunta foi "construir o motor de geração de ocorrências futuras
   agora?" — resposta: não, só o campo recurrence_rule como metadado,
   porque Bill (Fase 6) ia precisar do mesmo conceito e não fazia
   sentido construir o motor duas vezes. Quando a Fase 6 chegou, a
   pergunta foi feita de novo (agora que Bill realmente precisava) — e
   a resposta continuou sendo "só metadado por enquanto". É um exemplo
   real de não expandir escopo só porque "chegou a hora", mesmo tendo
   sido a própria justificativa usada pra adiar da primeira vez.

f) Comunicação entre módulos por chamada direta de serviço, não evento
   assíncrono — BillService.pay() chama TransactionService.create()
   diretamente (mesmo padrão já previsto no roadmap arquitetural desde
   antes de Bill existir: "BillService chama TransactionService ao
   registrar pagamento"). Dentro da mesma transação, então se a criação
   da transaction falhar, a baixa do bill reverte inteira — nenhum
   estado parcial ("bill marcado como pago mas sem lançamento
   correspondente") é possível.

g) Saldo contábil vs. saldo disponível, calculados juntos no Dashboard
   — contábil soma todo lançamento POSTED, disponível só os com
   transactionDate até hoje. Existe pra evitar a ambiguidade clássica de
   apps financeiros mal feitos: um lançamento futuro já marcado como
   POSTED (ex.: salário agendado pra semana que vem) não deveria inflar
   "quanto eu tenho agora".

h) Padrão de autorização replicado em todo módulo financeiro, testado
   sistematicamente — todo *IT do projeto (AccountIT, CategoryIT,
   BudgetIT, TransactionIT, BillIT) tem pelo menos um teste registrando
   dois usuários (dois households automáticos) e confirmando que um
   nunca lista/lê/atualiza/exclui dado do outro. E toda validação de
   campo de payload que referencia outro módulo (accountId numa
   transaction, categoryId num budget) segue a mesma regra: inválido ou
   não visível ao household vira 400 (IllegalArgumentException), nunca
   404 — 404 é reservado pro recurso primário do próprio endpoint,
   nunca pra um campo dentro do corpo da requisição.

i) O ciclo "implementei → mvn verify → achei bug real → corrigi" se
   repetiu, e não só na Fase 1 (ver histórico antigo) — na Fase 5, ao
   rodar a suíte depois de implementar transferência, dois bugs reais
   apareceram: (1) a coluna transfer_pair_id estava mapeada com
   updatable=false, que descarta silenciosamente qualquer UPDATE nela —
   o cancelamento em cascata da perna pareada simplesmente não
   funcionava, porque o id nunca chegava ao banco (só sumia sem erro,
   sem warning); e (2) um filtro de data opcional (competenceMonth)
   quebrava no Postgres com "could not determine data type of
   parameter" porque o parâmetro só aparecia num "? IS NULL" sem
   comparação direta com a coluna na mesma posição — corrigido com
   CAST(:param AS date). Os dois viraram teste de regressão antes do PR
   ser aberto (ver seção 5 para o detalhe de como cada um foi isolado).


4. TEMAS PARA ESTUDAR
------------------------
Cada tema abaixo está amarrado a algo específico que você vai encontrar
neste código — não é lista genérica.

- Multi-tenancy por "espaço compartilhado" (household) vs. por usuário
  direto: por que household_id em vez de user_id muda a query de
  autorização de "é meu?" para "eu pertenço ao dono disso?", e por que
  essa mudança é muito mais barata de fazer ANTES de existir dado do que
  depois (migração de toda tabela + toda checagem de authorization).

- Padrão "derivado, nunca persistido" para dado calculável: quando vale
  a pena recalcular toda leitura (Budget.spent, Bill OVERDUE, Dashboard
  inteiro) em vez de manter um campo sincronizado via trigger/job/
  evento. Trade-off: mais barato e sem risco de inconsistência, mas cada
  leitura custa uma query a mais — só compensa em volume baixo/médio,
  não em dashboards de alta escala.

- Projeções JPA (interfaces com getters, ex. AccountBalanceProjection)
  e JPQL com CASE WHEN + agregação (SUM condicional por tipo de
  lançamento) — como o Spring Data JPA mapeia uma query de agregação
  pra uma interface sem precisar de uma entidade JPA completa nem DTO
  manual com construtor de projeção.

- Enum literal totalmente qualificado em JPQL
  (com.mecfin.transaction.domain.TransactionType.INCOME) dentro de um
  CASE WHEN — alternativa a comparar string literal contra coluna
  @Enumerated(STRING), mais seguro a refactor (renomear o enum quebra
  compilação, não silenciosamente em runtime).

- Spring Data Page/Pageable e por que nunca devolver
  org.springframework.data.domain.Page direto num controller — a
  PagedResponse<T> deste projeto (shared.web) é o padrão de envelope
  pra desacoplar o contrato da API da representação interna do Spring
  Data, que pode mudar entre versões.

- Condição de corrida check-then-act em constraint única, e o mesmo
  idioma (saveAndFlush + catch de DataIntegrityViolationException)
  reaplicado em dois lugares diferentes do projeto por dois motivos
  diferentes: AuthService.register (email único) e BudgetService.create
  (unique constraint household+categoria+mês) — vale comparar os dois
  para ver que é o MESMO padrão resolvendo dois problemas de negócio
  diferentes, não uma coincidência.

- @Column(updatable = false) e por que ele silenciosamente ignora
  qualquer UPDATE, sem lançar exceção nem warning — e por que isso é
  perigoso especificamente em referências mútuas (duas linhas que
  precisam apontar uma pra outra), onde pelo menos uma delas
  estruturalmente precisa de um UPDATE pós-insert genuíno.

- Inferência de tipo de parâmetro JDBC no Postgres: por que um parâmetro
  usado só em "? IS NULL" (nunca comparado diretamente contra uma
  coluna tipada na mesma posição) não dá contexto suficiente pro
  planner inferir o tipo, mesmo com um valor não-nulo em runtime — e
  por que CAST(:param AS tipo) resolve sem mudar a semântica da query.

- Modelagem de dinheiro/data em transferência e parcelamento: por que
  amount é sempre armazenado como magnitude positiva com um campo type/
  direction separado (em vez de sinal embutido no valor), e por que
  competence_month é um campo separado de transaction_date (fatura de
  cartão fechada num mês, competência em outro — mesmo raciocínio já
  seria necessário pra Fase 8/cartão de crédito).

- Cookie de sessão vs JWT, Argon2id, RFC 7807, IDOR/BOLA via
  CurrentUser, Testcontainers — temas já cobertos pela versão anterior
  deste arquivo (Fases 0-1), continuam válidos e agora têm muito mais
  código exercitando cada um (ex.: IDOR/BOLA testado sistematicamente
  em 5 módulos financeiros, não só documentado em comentário).


5. DIFICULDADES/PROBLEMAS REAIS ENCONTRADOS
-----------------------------------------------
Bem mais rico agora que existem 8 fases de histórico real:

a) Os dois bugs da Fase 5 (transferência/parcelamento) — encontrados
   rodando mvn verify antes de abrir o PR, não em produção:
     1. Cancelamento em cascata de transferência não funcionava: o teste
        de integração cancelava uma perna e a outra continuava POSTED.
        Isolado adicionando uma asserção extra que confirmava via GET
        numa request separada (não só a resposta imediata do POST, que
        só reflete o objeto em memória) que transfer_pair_id realmente
        tinha sido persistido — e não tinha. Causa raiz:
        updatable=false na coluna.
     2. Filtro de data opcional em /transactions quebrava com 500 e
        "could not determine data type of parameter $10" — mesmo com
        um valor de data válido informado. Causa: Postgres não conseguia
        inferir o tipo de um parâmetro usado só em "? IS NULL".
   Os dois viraram teste de regressão (TransactionIT) antes do PR #13
   ser aberto.

b) Correção de processo em cascata sobre o próprio histórico do repo
   (18-19/08/2026) — o usuário lembrou de ter instruído "sempre
   branch+PR, nunca commit direto" e "nunca trailer de co-autoria", e
   ao verificar o histórico real do fin-mec, várias fases (incluindo
   fases já mergeadas e, num primeiro diagnóstico errado, uma fase que
   na verdade JÁ tinha ido por PR real) precisaram ser reorganizadas.
   O processo revelou um erro de diagnóstico próprio no meio do caminho
   (assumir que uma fase tinha sido commitada direto quando na verdade
   tinha PR real, só que mergeado por rebase — sem merge commit visível
   no git log) — corrigido antes de causar dano (force-push só depois
   de confirmar com gh pr list). Resultado: histórico inteiro
   reescrito, PRs #7-#10 recriando fases 0-2 retroativamente sem
   trailer de co-autoria, sem perder nenhum conteúdo (confirmado por
   diff de árvore antes/depois). Lição prática registrada em memória:
   auditar Co-Authored-By num repo pequeno sempre com `git log --all`
   sem limitar quantidade — um `git log -5` recente escondeu 2 dos 4
   commits afetados na primeira checagem.

c) Decisão de ordem de implementação forçada por dependência real —
   Budget (Fase 4 do roadmap original) precisa de Transaction (Fase 5)
   pra calcular gasto realizado de verdade. Em vez de implementar Budget
   com um placeholder ("gasto = 0, sempre"), a decisão foi adiantar um
   Transaction mínimo (só receita/despesa, sem transferência/parcela/
   recorrência) dentro da própria Fase 4, e completar o resto de
   Transaction na Fase 5 depois. Evitou construir código que seria
   descartado, ao custo de fase 4 "invadir" escopo da fase 5.

Fora esses três pontos, a execução das 8 fases foi bastante linear —
cada fase seguiu o padrão já estabelecido nas anteriores (schema →
domain/infra → application → api → testes, em commits separados dentro
de uma branch, PR aberto, merge só depois de confirmação explícita).


6. COMO EXPLICAR ESSE PROJETO PRA ALGUÉM DE FORA
-----------------------------------------------------
"O mec-fin é um app pessoal de controle financeiro com o MVP completo:
dá pra cadastrar contas, categorizar receitas e despesas, lançar
transações (incluindo transferência entre contas e compras parceladas),
definir um limite de gasto por categoria por mês, cadastrar contas a
pagar com baixa de pagamento, e ver um dashboard com saldo, previsão e
gastos por categoria — tudo isso com autenticação segura e isolamento
completo entre usuários diferentes. O espelho de mercado é o Organizze,
mas com uma diferença de propósito desde o início: em vez de "uma conta
compartilhada por credencial" (como o próprio Organizze faz hoje), este
projeto já modela um espaço financeiro (household) com membros e papéis
próprios — hoje é transparente (você só tem sua própria conta), mas a
base pra dividir as finanças com outra pessoa, cada um com seu próprio
login, já existe sem precisar reescrever nada depois.

O que mais vale destacar tecnicamente não é uma feature isolada, é a
disciplina que se repete: dado calculável (quanto foi gasto, se uma
conta está vencida, o dashboard inteiro) nunca é guardado — é sempre
recalculado na hora, pra nunca ficar dessincronizado. Toda vez que um
módulo precisa referenciar outro (uma transação apontando pra uma
conta, um orçamento apontando pra uma categoria), a mesma regra de
autorização se repete e é testada: se não pertence ao seu espaço
financeiro, você nunca enxerga, nem por engano. E quando um bug real
apareceu — duas vezes, em fases diferentes — foi encontrado rodando a
suíte de testes antes de abrir o pull request, não depois."
